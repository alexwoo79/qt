## 例题 3-1 多继承：一个对象里为什么有两个 vptr

**目标**：理解"对象首地址 ≠ 每个基类子对象的地址"，以及三种指针转换的区别。

**代码**：`code/p3_01_multi_inherit.cpp`（`struct C : A, B`，A、B 都有虚函数）

**真实输出**

```text
sizeof(A)=16 sizeof(B)=16 sizeof(C)=32
  pc = 0x16b09a448（对象首地址）
  pa = 0x16b09a448（A 子对象，偏移 0）
  pb = 0x16b09a458（B 子对象，偏移 16）
两个子对象各有一张虚表：
  A 子对象的 vptr = 0x104d68030
  B 子对象的 vptr = 0x104d68060
C::fa()（重写 A 的）
C::fb()（重写 B 的）
-- 指针调整是编译器做的，不是免费的 --
  static_cast<B*>(pc)      = 0x16b09a458（正确，从对象首地址偏移到 B 子对象）
  reinterpret_cast<B*>(pa) = 0x16b09a448（错，等于把 A 子对象当 B 用 → UB）
  dynamic_cast<B*>(pa)     = 0x16b09a458（正确，代价是运行时检查）
```

**讲解**

1. `sizeof(C)` = 32：A 子对象（vptr+int = 16）+ B 子对象（vptr+int = 16）+ `int c` 塞进 A 后面的填充里，正好 32。
2. 同一个对象，`pa` 和 `pb` **差 16 字节**——指针类型不同，指向的是不同子对象。
3. 两个子对象各有 vptr，指向各自的虚表：这就是"多继承对象里有多个 vptr"的原因。
4. `reinterpret_cast<B*>(pa)` 只是**按字节重解释**，不做偏移；用它调 `fb()` 会跳到 A 的表上，是彻底的 UB。`static_cast` 知道继承关系会自动偏移，`dynamic_cast` 还能做跨类转换（代价是运行期检查）。
5. 跨语言/跨模块的接口设计里，这条最容易出事：**永远通过基类指针 + `static_cast`/`dynamic_cast`，不要 `reinterpret_cast` 到另一个基类**。

**动手改一改**：让 `C` 只继承 `A`，其余不变，观察 `pa/pb` 是否重合、sizeof 变成多少，解释为什么。

**常见误区**：以为"多态指针转换不用代价"。多继承下每次从派生类指针转到第二个基类，都要做一次加法。

**Rust 对照**：Rust 没有多继承，用 trait 组合 + `dyn` 实现等价能力，代价是"同一对象的多张表"由胖指针分别携带。

**验收问题**：为什么 `static_cast<B*>(pa)` 连编译都过不了（A 和 B 无继承关系），而 `dynamic_cast` 可以？

## 例题 3-2 菱形继承与虚继承：两份基类还是一份

**目标**：看到"数据冗余"和"虚继承的额外指针"，理解虚继承为什么慢一点。

**代码**：`code/p3_02_virtual_inherit.cpp`

**真实输出**

```text
sizeof(Base)=16 sizeof(Left)=16 sizeof(Diamond)=32
→ Diamond 里有两份 Base（2 个 vptr + 2 个 int）
sizeof(VLeft)=24 sizeof(VRight)=24 sizeof(VShape)=32
→ 虚继承后只有一份 Base，多出来的是指向公共 Base 的 vbptr
[非虚继承]
  d.Left::value=1 落在 0x16d306440
  d.Right::value=2 落在 0x16d306450
  两个 Base 子对象地址相差 16 字节，写 d.value 会报二义性编译错误。
[虚继承]
  &s.value = 0x16d306420，VLeft* 与 VRight* 指向的公共 Base 相同：是
VShape::show() value=99（唯一一份 Base）
```

**讲解**

1. 非虚菱形继承里 `Diamond` 有**两份** `Base`：`d.Left::value` 和 `d.Right::value` 是两块不同内存；写 `d.value` 直接编译报二义性。
2. `VLeft`/`VRight` 比 `Left`/`Right` 大（24 vs 16）：虚继承的代价是**多一个 vbptr**，运行期通过偏移表定位那份唯一的 `Base`。
3. 虚继承下 `s.value` 只有一份，不需要限定名；两条路径拿到的 `Base*` 是同一个地址。
4. 通过左路指针调用 `show()` 仍然走到 `VShape::show()`——虚表在这条路径上也是正确的。
5. 实务建议：**能用组合就别用菱形继承**；虚继承是"不得不共享同一份基类"时的工具，代价是每次访问多一次间接寻址。

**动手改一改**：把 `VShape::show()` 里的 `override` 去掉，重新编译，看编译器怎么报"没有可重写的虚函数"。

**常见误区**：以为"虚继承 = 虚函数"。两者无关：虚继承解决的是**数据冗余（菱形）**，虚函数解决的是**行为多态**。

**验收问题**：`sizeof(VLeft)=24` 里，除了 `Base` 的数据，还多了什么？

## 例题 3-3 / 3-4 / 3-5 三类内存错误与 ASan 的读法

**目标**：会读 ASan 报告——看错误类型、看地址、看"谁分配的/谁释放的"。

三个例子都要用 ASan 编译（macOS 上不支持 `detect_leaks`，用 `abort_on_error=0`）：

```bash
clang++ -std=c++17 -g -O0 -fsanitize=address code/p3_03_overflow.cpp -o /tmp/p3_03
ASAN_OPTIONS=abort_on_error=0 /tmp/p3_03
```

### 3-3 堆越界写

```text
正常写完 4 个元素：arr[3]=3
下面故意越界写 arr[4]……
==76532==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x602000000100
WRITE of size 4 at 0x602000000100 thread T0
    #0 0x000100b28a28 in main p3_03_overflow.cpp:11
0x602000000100 is located 0 bytes after 16-byte region [0x6020000000f0,0x602000000100)
allocated by thread T0 here:
    #0 0x0001012d0268 in _Znam+0x74 (libclang_rt.asan_osx_dynamic.dylib)
```

读法：`heap-buffer-overflow` + `WRITE of size 4` = 往堆上写了 4 字节；`is located 0 bytes after 16-byte region` 说明越过了 16 字节（4 个 int）的边界；`allocated by ... _Znam` 就是 `operator new[]`（用 `c++filt _Znam` 可以还原）。

### 3-4 释放后使用（野指针）

```text
分配：p=0x6020000000f0 值=7
已 delete p，但指针变量还在（这就是野指针）
==76560==ERROR: AddressSanitizer: heap-use-after-free on address 0x6020000000f0
READ of size 4 at 0x6020000000f0 thread T0
    #0 0x00010040ca00 in main p3_04_use_after_free.cpp:11
0x6020000000f0 is located 0 bytes inside of 4-byte region
freed by thread T0 here:
    #0 0x000100b8c558 in _ZdlPv+0x74 (libclang_rt.asan_osx_dynamic.dylib)
```

读法：`heap-use-after-free` 里"freed by"那一段会告诉你**在哪释放的**——把两处代码一对比，问题一目了然。修复习惯：`delete` 后立刻 `p = nullptr`。

### 3-5 重复释放

```text
-- 正面：所有权写进类型里，就没有第二次释放的机会 --
  unique_ptr 管着 2，作用域结束自动释放一次
-- 反面：裸指针 delete 两次 --
==76566==ERROR: AddressSanitizer: attempting double-free on 0x6020000000f0
    #0 0x000104918558 in _ZdlPv+0x74 (libclang_rt.asan_osx_dynamic.dylib)
    #1 0x0001041b0ad0 in main p3_05_double_free.cpp:11
freed by thread T0 here:
    #0 0x000104918558 in _ZdlPv+0x74 (libclang_rt.asan_osx_dynamic.dylib)
    #1 0x0001041b0a74 in main p3_05_double_free.cpp:9
```

读法：`attempting double-free` 会同时给出"这次释放"和"上次释放"的调用栈（本机是第 11 行与第 9 行）——不需要猜。

## 例题 3-6 综合项目：多态成绩管理（零泄漏）

**目标**：把前 11 周的东西组装成一个能讲清内存过程的程序。

**代码**：`code/p3_06_project.cpp`（`Student` 纯虚接口 + 三个派生类 + `GradeBook` 用 `vector<unique_ptr<Student>>` + `fstream` 持久化）

**真实输出（节选）**

```text
sizeof(Regular)=40 sizeof(Honors)=40 sizeof(Makeup)=40（都含 vptr）
-- 构建名册 --
  构造 Tom      对象 @ 0x101411490
-- 名册（按对象真实类型多态求值）--
  Tom      优等生 卷面  85.0 → 总评  97.7
  Jerry    普通生 卷面  78.0 → 总评  78.0
  Spike    补考生 卷面  60.0 → 总评  54.0
  平均总评 = 76.58
  首个对象的 vptr = 0x100b90010（基类指针 + 虚表 → 多态的机械本质）
-- 持久化（ofstream RAII，无需手动 close）--
  保存到 /tmp/cpp_gradebook.txt：成功
-- 读回来（工厂 + unique_ptr 重新建对象）--
  …同样三行结果，平均总评 76.58
  析构 Spike / Jerry / Tom（逆序）
所有对象已按构造的逆序释放，没有裸 new/delete，也没有泄漏。
```

**讲解**

1. **接口在基类**：`finalScore()` 纯虚（算法各不相同），`describe()` 是基类实现里调用虚函数——一处写、处处正确。
2. **所有权在类型里**：`GradeBook` 只持有 `vector<unique_ptr<Student>>`，容器搬家靠移动；没有裸 `new/delete`，也就没有 double free 的机会。
3. **虚析构是必需品**：`delete` 通过 `unique_ptr<Student>` 发生，靠 `virtual ~Student()` 才能完整析构派生类。
4. **持久化也是 RAII**：`ofstream`/`ifstream` 离开作用域自动关闭，连 `close()` 都不用写。
5. **工厂 + 所有权**：`load()` 里根据类型字符串创建不同派生类，返回 `unique_ptr` 交给容器——**创建与释放责任清晰**。
6. 最后一批输出就是验收证据：所有对象按构造逆序析构，账目归零。

## 例题 3-7 排坑四步法：对象切片、悬空引用、容器扩容

**目标**：学会"不用调试器也能定位"的手法——打印地址、sizeof、vptr、size/capacity，对照正常与异常路径。

**代码**：`code/p3_07_diagnose.cpp`

**真实输出（节选）**

```text
=== 现场 1：对象切片 ===
  原始对象：sizeof=16 vptr=0x1049e4010
Derived 原始   @0x16b41e3f0 : 10 40 9e 04 01 00 00 00 07 00 00 00 44 00 00 00
  byRef  收到的对象：sizeof=16 vptr=0x1049e4010 who()=Derived
  byValue 收到的对象：sizeof=16 vptr=0x1049e4060 who()=Base
=== 现场 2：悬空引用 ===
  作用域内 local @0x16b41e3b0 内容="临时字符串"
  local 已销毁，但我们还拿着地址 0x16b41e3b0
=== 现场 3：容器扩容后旧引用失效 ===
  扩容前 names.data()=0x1051c5e80，first 引用地址 0x1051c5e80
  扩容后 names.data()=0x1051c6150，capacity=32
=== 排坑四步法 ===
  1. 复现  2. 观测  3. 对比  4. 验证
```

**讲解**

1. **对象切片**：`byValue(Base b)` 只复制 `Base` 那部分。证据是 `vptr` 从 `…010` 变成 `…060`，`who()` 也跟着变成 `Base`——**没有崩溃，但行为已经错了**，这类 bug 最难查。
2. **悬空引用**：作用域结束后地址还在，内容却可能"看起来正常"。所以判断悬空的正确方式是**看所有权，而不是看值**。
3. **容器扩容**：`names.data()` 从 `0x1051c5e80` 变成 `0x1051c6150`，之前拿到的引用就悬空了。修法：先 `reserve`，或改用下标/迭代器重新取。
4. **四步法**：复现（20 行内）→ 观测（地址/大小/计数）→ 对比（正常 vs 异常路径的字节差异）→ 验证（ASan/UBSan 复跑全绿）。

**动手改一改**：把现场 1 改成"返回基类对象的函数"（`Base make() { Derived d; return d; }`），体会**返回值也会切片**，然后用 `unique_ptr<Base>` 修好。

**验收问题**：对象切片为什么"不报错但很危险"？用哪个信号能最快发现它？
