# 第二阶段例题讲解（第 3–6 周：容器底层 / RAII / 智能指针）

> 这一阶段的主题只有一个：**谁拥有这块内存、它活到什么时候**。每道例题都让你先看到现象（容量、地址、计数），再总结规则。

## 例题 2-1 std::string：SSO 与扩容

**目标**：知道"字符串对象里有什么"，并说清 `reserve` 到底省了什么。

**代码**：`code/p2_01_string.cpp`（打印 `size/capacity/data`，并用地址判断数据在对象内部还是堆上）

**真实输出（节选）**

```text
sizeof(std::string) = 24（libc++：指针/长度/容量 24 字节，SSO 缓冲嵌在里面）
短字符串 size= 2 capacity=22 data=0x16b0b6450 SSO=内部缓冲
20 字符  size=20 capacity=22 data=0x16b0b6438 SSO=内部缓冲
31 字符  size=31 capacity=31 data=0x1055a5500 SSO=堆上
长度 22：capacity=22 data=0x16b0b63f8
长度 23：capacity=47 data=0x1055a6f40  ← 已经在堆上了
reserve(64) 后：capacity=71 追加 40 次，data 地址没变（一次分配搞定）
```

**讲解**

1. `sizeof(std::string)` = 24，但容量可以到 22——因为**小字符串直接存在这 24 字节里**（SSO，短字符串优化）。
2. 判断依据不是猜的：把 `s.data()` 和 `&s` 比较，落在对象内部就是 SSO，落在堆区间就是堆分配。
3. 22 → 23 那一刻地址跳到 `0x1055…`（堆），容量从 22 直接跳到 47：**扩容是"重新申请 + 拷贝 + 释放旧的"**。
4. `reserve(64)` 之后连续 append 40 次地址没变（本机容量按 1.5 倍长成 71），说明预留容量把多次分配变成一次。

**动手改一改**：把循环上限改成 1000，打印每次**容量变化**而不是每次长度，数一数一共分配了几次；再试 `reserve(1000)` 对比。

**常见误区**：以为 `capacity()` 是"用掉的内存"。它是"当前缓冲区能装多少"，且**不保证**等于 size。

**Rust 对照**：`String` 也是"指针+长度+容量"三件套（24 字节），同样有 `reserve`；不同点是 Rust 里对字符串切片有借用检查，越界/悬空在编译期就被拦。

**验收问题**：为什么 `const char* p = s.c_str();` 之后一旦 `append`，`p` 就可能失效？

## 例题 2-2 std::vector：扩容、移动、迭代器失效

**目标**：把"均摊 O(1)、迭代器失效"落到具体地址和计数上。

**代码**：`code/p2_02_vector.cpp`（`Tracked` 统计拷贝/移动次数；打印扩容时 data 地址）

**真实输出（节选）**

```text
push_back( 0) → size= 1 capacity= 1 data=0x1050ed7a0  ← 发生重分配
push_back( 1) → size= 2 capacity= 2 data=0x1050ed4a0  ← 发生重分配
push_back( 2) → size= 3 capacity= 4 data=0x1050ed7a0  ← 发生重分配
push_back( 4) → size= 5 capacity= 8
push_back( 8) → size= 9 capacity=16
push_back(16) → size=17 capacity=32
容量序列大致是 1,2,4,8,16,32：libc++ 按 2 倍增长，均摊 O(1)。
插入 8 个元素后：存活=8 拷贝=0 移动=7
vector 离开作用域后：存活=0（全部析构，没有泄漏）
扩容前 data=0x1050ed7a0
push_back 后 data=0x7eb000960，旧指针 已悬空（继续解引用就是 UB，ASan 会抓到）
reserve 之后 data=0x1050ef030，之前那个指针同样失效
```

**讲解**

1. 容量序列 1→2→4→8→16→32：**每次翻倍**，所以 n 次 push_back 的总拷贝是 O(n)，均摊到每次是 O(1)。
2. 注意地址会"绕回来"（`0x1050ed7a0` 出现两次）——分配器回收后复用，这是正常现象，别用地址判断"是否同一个数组"。
3. 自定义类型那一段是重点：**拷贝=0、移动=7**。因为 `Tracked` 的移动构造是 `noexcept`，vector 扩容时走移动而不是拷贝。
4. 把 `noexcept` 去掉（动手改），拷贝次数立刻上升——这就是"移动构造为什么要标 noexcept"的直接证据。
5. 最后一段：扩容后旧 `data()` 指针**悬空**；`reserve` 同样会让之前的指针失效。**规则：只要发生重分配，指向元素的指针/引用/迭代器全部作废。**

**动手改一改**：① 去掉移动构造的 `noexcept`，对比拷贝/移动计数；② 在循环前 `v.reserve(17)`，看还会不会发生重分配。

**常见误区**：以为"迭代器失效只发生在 push_back 时"。`reserve`、`insert`、`erase`、甚至别的线程的写操作都会让迭代器失效。

**Rust 对照**：`Vec` 同样有容量与 2 倍增长；不同点是**借用检查器在编译期禁止"一边持有元素引用一边扩容"**，C++ 只能靠约定和 ASan。

**验收问题**：为什么"均摊 O(1)"不等于"每次都很快"？

## 例题 2-3 RAII：把释放交给析构函数

**目标**：证明"异常、提前 return、扩容搬家"都不会漏掉释放。

**代码**：`code/p2_03_raii.cpp`（`Buffer` 禁止拷贝、允许移动；用 `g_outstanding` 当内存账本）

**真实输出（节选）**

```text
[RAII 版本]
  构造 first   ：申请 1024 字节 @ 0x100d06f80（账本=1）
  构造 second  ：申请 2048 字节 @ 0x100d07380（账本=2）
  析构 second  ：释放 @ 0x100d07380（账本=1）   ← 逆序析构
  析构 first   ：释放 @ 0x100d06f80（账本=0）
[裸指针版本]
  new 了 1024 字节 @ 0x100d06f80，但忘了 delete
  账本 = 1  ← 这 1 就是泄漏
[中途抛异常]
  构造 guard   ：申请 512 字节 @ 0x100d07380（账本=1）
  析构 guard   ：释放 @ 0x100d07380（账本=0）   ← 异常路径也执行析构
[把 Buffer 放进 vector：只移动，不拷贝]
  构造 pool-3  ：申请 512 字节 @ 0x100d07690（账本=3）
  移动 pool-1  ：指针移交给新对象（账本不变=3）
  移动 pool-2  ：指针移交给新对象（账本不变=3）
  vector 销毁后账本 = 0
```

**讲解**

1. **逆序析构**：后构造的先析构。这是 C++ 的保证，也是"依赖关系"的体现（后建的对象可能引用先建的）。
2. 裸指针版少一次 `delete`，账本停在 1：**泄漏不是"内存不够"，而是"账目不平"**——这正是 ASan/LSan 抓的东西。
3. 抛异常那段是 RAII 的核心价值：`throw` 之后栈展开（stack unwinding），`guard` 的析构照样执行。裸指针做不到这一点。
4. 放进 `vector` 时触发扩容：`pool-1/pool-2` 被**移动**（账本不变=3），说明移动只是"指针搬家"，没有二次申请内存。
5. `Buffer` 删掉了拷贝构造——因为"独占资源"的语义一旦允许拷贝，就会 double free。**能编译通过的类型，才能安全地被误用。**

**动手改一改**：给 `Buffer` 加一个 `swap`，用 `swap` 实现移动赋值，并解释为什么这样更安全（自赋值/异常）。

**常见误区**：以为"写了析构函数就 RAII 了"。真 RAII 还要求：禁止或正确实现拷贝/移动，否则会 double free 或泄漏。

**Rust 对照**：Rust 的 `Drop` 就是析构，且**所有权唯一**，编译器自动禁止"复制后两个对象都以为自己该释放"。

**验收问题**：为什么 `Buffer(const Buffer&) = delete;` 比"写了拷贝构造但小心使用"更安全？

## 例题 2-4 unique_ptr：把所有权写进类型

**目标**：理解 move 之后源指针为什么为空；知道什么时候该按引用传、什么时候该按值传。

**代码**：`code/p2_04_unique_ptr.cpp`

**真实输出（节选）**

```text
-- 构造与自动释放 --
  构造 Resource(1)
  observe 里看到的 id=1（所有权还在调用方）
  析构 Resource(1)                        ← 离开作用域自动释放
-- 移动：所有权转移，源指针变空 --
  move 前 owner=0x1011bd4e0
  move 后 owner=0x0（空） thief=0x1011bd4e0
-- 传参把所有权交出去 --
  构造 Resource(3)
  consume 里看到的 id=3
  析构 Resource(3)                        ← 函数结束即释放
-- 放进容器：只移动，指针稳定 --
  容器里 3 个对象，析构顺序与构造相反：
  析构 Resource(6) / Resource(5) / Resource(4)
-- 数组形式与自定义删除器 --
  unique_ptr<int[]> arr[0]=42（析构用 delete[]）
  自定义删除器：FILE* = 已打开
```

**讲解**

1. `observe(const unique_ptr&)`：**借用**，不转移所有权，函数内不能用它去删除。
2. `std::move(owner)` 之后 `owner.get() == nullptr`：这就是 Rust move 的同款语义（源变空、目标接管）。
3. `consume(unique_ptr)`：按值传参 = **交出所有权**，函数结束自动释放——这个签名本身就是文档。
4. 放进 `vector` 时只发生移动，指针值稳定（`make_unique` 分配的地址不变），容器析构时逆序释放。
5. 数组形式用 `delete[]`；自定义删除器让你能管 `FILE*`、socket、平台句柄——**RAII 不限于 new/delete**。

**动手改一改**：写一个 `class Session { std::unique_ptr<Resource> res_; }`，实现移动构造，把"能移动不能拷贝"的语义往上传递。

**常见误区**：给 `unique_ptr` 调用 `.get()` 后手动 `delete` —— 那是把所有权又拿回手里，必然 double free。

**Rust 对照**：`Box<T>` ≈ `unique_ptr<T>`；Rust 的借用 `&T`/`&mut T` 对应 C++ 的 `const&`/`&`，但规则由编译器强制。

**验收问题**：为什么"按 const 引用接收 unique_ptr"和"按值接收"表达的是两种完全不同的意图？

## 例题 2-5 shared_ptr：引用计数、循环引用与 weak_ptr

**目标**：看到计数变化，并亲手制造一次泄漏、再用 `weak_ptr` 修好。

**代码**：`code/p2_05_shared_ptr.cpp`

**真实输出（节选）**

```text
[引用计数变化]
  构造 Node(1)
  make_shared 后 use_count=1
  拷贝一份后 use_count=2
  副本销毁后 use_count=1
  move 之后：源=空，新=1
  析构 Node(1)
[循环引用]
  构造 Node(2) / 构造 Node(3)
  离开作用域前：use_count x=2 y=2
  （上面没有 Node(2)/Node(3) 的析构 —— 计数永远不归零）
[用 weak_ptr 破环]
  构造 Node(4) / 构造 Node(5)
  离开作用域前：x.use_count=1 y.use_count=2
  弱引用能临时提升为强引用，看到 Node(4)
  析构 Node(4)
  析构 Node(5)
```

**讲解**

1. 拷贝 `shared_ptr` → 计数 +1；副本销毁 → 计数 -1；`move` 不改变计数（只是换了持有者）。
2. 循环引用那一段：两个对象互相持有，计数**永远停在 2**，析构函数不执行——**这就是泄漏，而且和 new/delete 没关系**。
3. `weak_ptr` 不增加计数：`y->back = x` 之后 `x.use_count()` 仍是 1。
4. `weak_ptr::lock()` 会**临时**提升为 `shared_ptr`；提升失败（对象已销毁）返回空——所以弱引用的使用方式永远是"lock 后判空"。
5. 观察者、缓存、回调注册这些场景都应该用 `weak_ptr`，避免"宿主被观察者拖住不释放"。

**动手改一改**：把循环引用版本用 ASan 跑一次看 leak 报告；再把 `next` 改成 `weak_ptr`，确认析构恢复。

**常见误区**：以为 `shared_ptr` 是万能解。它是**共享所有权**的显式表达，滥用会把"生命周期"从代码结构里藏进运行期计数——排查难度反而更高。

**Rust 对照**：`Rc<T>`/`Arc<T>` 同样是共享计数，但 Rust 在编译期不允许可变别名；`Weak<T>` 与 `weak_ptr` 一一对应。

**验收问题**：什么样的情况下，用 `shared_ptr` 反而不如 `unique_ptr` 安全？
